# Documentation conventions

This project is currently in requirements and scope definition. Documentation should preserve the reasoning behind the product before implementation details are introduced.

## Working principles

- Write for a mixed audience of aviation, energy, operations, and product stakeholders.
- Use plain language and define technical terms when they first appear.
- Separate confirmed requirements from assumptions, open questions, and ideas.
- Use SI units where practical; show the unit beside every value.
- Treat aircraft specifications as source-backed inputs, not universal truths.
- Identify the aircraft, mission, operating conditions, and source date for any modeled value.

## Requirement format

When capturing a requirement, include:

1. A short title.
2. The user or operational need.
3. The expected behavior or decision the product should support.
4. Relevant assumptions and exclusions.
5. Open questions or follow-up decisions.

## Decision language

- **Confirmed:** agreed scope or behavior.
- **Proposed:** a candidate direction awaiting discussion.
- **Assumption:** a temporary input used to continue ideation.
- **Open question:** unresolved and requiring a decision.

## Aircraft and charging references

Joby may be used as a guidepost, but references to Joby or any other manufacturer should not be treated as endorsement, complete technical disclosure, or a substitute for validated operating data.
